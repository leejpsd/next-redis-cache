# 왜 이 프로젝트에서는 SSG를 실험 대상에 넣지 않았나

## 결론

SSG는 훌륭한 전략이지만, **이 프로젝트가 증명하려는 문제(멀티 인스턴스 캐시 일관성)와 본질적으로 맞지 않는다**. 그래서 4편 비교에서도 SSG 데모 경로는 만들지 않았다. 대신 여기서는 "왜 SSG가 이 맥락에 안 맞는지"를 네 가지 관점으로 정리한다.

## 1. 데이터 성격

이 프로젝트의 모든 실험 경로가 바라보는 원본은 `https://randomuser.me/api/` 다. 요청할 때마다 다른 유저 객체를 돌려준다. 즉 **빌드 시점에 결과가 고정될 수 없는 데이터**다.

SSG가 자연스러운 데이터는 그 반대에 있다.

- 블로그 포스트 (발행 시점에만 결정)
- 제품 상세 페이지 (운영자가 드물게 수정)
- 이용약관, FAQ, 회사 소개 같은 정적 콘텐츠
- 이번 시리즈의 블로그 글 자체

즉 **"배포 시점에 진리값이 결정되는 콘텐츠"에만 SSG가 의미가 있다**. 이 프로젝트가 증명하려는 "여러 인스턴스가 같은 캐시 상태를 공유하는가"라는 질문은, 빌드 시점에 값이 고정되는 콘텐츠에서는 아예 제기되지 않는다.

## 2. 멀티 인스턴스 캐시 일관성 관점

이 시리즈의 1~3편은 이런 구도를 다뤘다.

- 여러 EC2/ECS 태스크가 같은 ALB 뒤에 있음
- 각 태스크가 자기 메모리/파일시스템에 캐시를 들고 있으면 **태스크마다 상태가 갈라짐**
- Redis 공유 캐시로 일원화해서 같은 응답을 보장

**SSG는 이 문제와 무관하다.** 이유는:

- SSG 결과물은 빌드 산출물(`.next/...`)에 HTML로 박힘
- 모든 태스크가 같은 이미지를 배포받으므로 **원천적으로 같은 파일을 서빙**
- 런타임 캐시 키, TTL, 무효화 같은 개념이 끼어들 여지가 없음

즉 SSG는 "그 문제를 풀지 않는다"가 아니라 **"그 문제가 발생할 수 없는 구조"**다. 이 시리즈의 핵심 논의(공유 캐시·무효화·일관성)는 SSG에 적용할 대상 자체가 없다.

## 3. 무효화 관점

이 프로젝트 실험의 핵심은 `revalidateTag`, `updateTag`, `cacheLife` 같은 **런타임 무효화 흐름**이다. SSG는 이 흐름의 바깥에 있다.

- SSG에서 데이터가 바뀌면 → **재빌드 + 재배포**가 기본
- Next.js의 On-Demand Revalidation(`revalidatePath`, `revalidateTag`)은 실제로는 ISR 경로를 다루는 것이고, 완전 정적 페이지에는 적용되지 않음
- 따라서 "태그 기반 부분 무효화" 같은 실험의 소재가 될 수 없음

3편에서 논의한 "메인 페이지는 섹션별로 다른 TTL을 가져야 한다" 같은 이야기도 SSG에서는 성립하지 않는다. 전부 빌드 결과물이거나 전부 런타임 렌더링이거나, 한쪽을 택해야 하기 때문이다.

## 4. 비용·성능 비교 맥락

SSG는 서버 렌더 비용이 0에 수렴하므로, **성능/비용만 따지면 항상 이긴다**. 다음과 같은 이유로 4편 비교표에 넣는 것이 오히려 혼란을 준다.

1. **비교 전제 위반**: SSR/ISR/Cache Components는 "매 요청마다 뭔가 결정해야 하는 동적 데이터"를 공유하는 문제를 푼다. SSG는 그 전제 자체가 없다.
2. **원본 API 비용 0**: origin fetch 수를 "배포당 n회"로 고정하면, "월 100만 요청 기준 origin fetch 감소량"이라는 축이 의미를 잃는다.
3. **일관성 이슈 없음**: 태스크 간 cache mismatch rate가 0%로 당연히 나오는데, 이것은 **"공유 캐시로 해결했다"가 아니라 "문제가 처음부터 없었다"**이므로 비교 대상이 되지 않는다.

## 5. 그렇다면 언제 SSG를 쓰는가

이 시리즈의 범위를 벗어나는 이야기지만 정리해둔다.

- 콘텐츠가 빌드 시점에 결정되고, 자주 바뀌지 않음
- 방문자마다 다른 내용을 보여줄 필요가 없음
- CDN 엣지까지 캐싱하고 싶음
- 배포 비용(빌드 시간, 재배포)이 운영 비용보다 낮음

위 조건을 다 만족하면 SSG가 최선이다. 이 프로젝트는 그중 어느 것도 해당하지 않으므로 다루지 않는다.

## 6. 4편 서술 방침

4편에서는 다음과 같은 톤으로 다룬다.

> SSG는 "데이터가 배포 시점에 고정되는 콘텐츠"에 최적이고, 그 가정이 성립하면 항상 비교 우위다. 그러나 이 시리즈에서 다루는 "멀티 인스턴스에서 동적 데이터 캐시를 공유하는 문제"는 SSG가 풀지 않는 영역이다. 그래서 비교 표에서는 제외하고, SSR/ISR/Cache Components/Hybrid/CSR/BFF 중에서 최선을 골랐다.

SSG를 "졌다"고 말하지 않고, **전제가 다른 도구로 구분**해서 독자 혼란을 줄인다.
